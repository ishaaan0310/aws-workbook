AWS Cloud Foundations & IAM

Intro to cloud computing · AWS Global Infrastructure · Shared Responsibility Model · IAM users, groups, policies, roles · IAM best practices

1.1 What is cloud computing?

In simple words: instead of buying servers (big upfront cost, weeks to set up, sized for the peak day), you rent computing power, storage and software over the internet, get it in minutes, and pay only for what you use — like electricity from the grid instead of your own generator.

Characteristics (from your slides + NIST)

  • On-demand self-service – click and get it.
  • Broad network access – ubiquitous access, business continuity.
  • Resource pooling / multi-tenancy – one physical pool serves many customers, isolated.
  • Rapid elasticity – capacity follows demand automatically.
  • Measured service – metered tariff, pay only for usage.
  • Optimal utilisation – harness under-used capacity via virtualisation.

Service models

  • IaaS – raw VMs, storage, network. You install the OS onwards. EC2, Google Compute Engine.
  • PaaS – platform ready; you only bring code & data. Elastic Beanstalk, Google App Engine, Heroku.
  • SaaS – finished software, monthly fee per user. Gmail, Office 365, Salesforce.

Deployment models & cloud layers

  • Public (AWS), Private (own cloud), Hybrid (both, connected), Community (e.g. govt – MeghRaj GI Cloud India, G-Cloud UK).
  • Virtualisation: a hypervisor (Xen, KVM, AWS Nitro) splits one physical server into many VMs.
  • Middleware = the "brain": orchestrates, schedules, provisions user requests.
  • Management layer: monitoring, metering, SLA, backup & DR.

1.2 AWS Global Infrastructure

In simple words: AWS has Regions (cities/countries like Mumbai, Singapore). Each Region has 2+ (usually 3) Availability Zones — separate buildings/groups of data centres with their own power and network, connected by fast private fibre. Edge locations are small sites in many more cities that cache content close to users.

  • How to choose a Region (exam favourite): ① Compliance / data residency (e.g. Indian bank data must stay in India) ② Latency – close to users ③ Service availability – not every service is in every Region ④ Cost – prices differ by Region.
  • Data never leaves a Region unless you move it — replication across Regions is controlled by you.
  • Deploying across 2+ AZs is the basic recipe for high availability. Deploying across Regions is for disaster recovery / global users.
  • Local Zones put compute near big cities for single-digit-ms latency; Regional edge caches sit between origin and edge locations.

1.4 IAM – Identity and Access Management

In simple words: IAM is the security guard + ID-card office of your AWS account. It decides who you are (authentication: password + MFA, or access keys) and what you can do (authorisation: policies). IAM is global (not per Region) and free.

The four pieces

  • Root user – the email that created the account; can do anything. Enable MFA, don’t use daily, no access keys.
  • IAM user – a person or app with long-term credentials (console password and/or access key ID + secret).
  • IAM group – a collection of users; attach policies once, all members inherit. Groups cannot contain groups.
  • IAM role – an identity with no permanent password/keys; anyone allowed can assume it and gets temporary credentials from STS. Used by EC2, Lambda, other accounts, federated (corporate / Google) users.

Policies

  • JSON document: Effect (Allow/Deny), Action (s3:GetObject), Resource (ARN), optional Condition (IP, MFA, time).
  • Identity-based – attached to user/group/role. One policy → many entities; one entity → many policies.
  • Resource-based – attached to the resource (S3 bucket policy) and has a Principal.
  • AWS-managed vs customer-managed vs inline policies.
  • Permissions boundary – maximum permissions a user/role can ever get.

IAM best practices (list 6–8 in exam)

  1. Lock away root user; enable MFA on it
  2. Least privilege – start with nothing, add only what’s needed
  3. Use groups to assign permissions to people
  4. Use roles (temporary credentials) for EC2/Lambda – never store access keys on servers
  5. Federation with an identity provider for humans
  6. MFA for all privileged users
  7. Rotate access keys; remove unused users, roles, keys
  8. Use policy conditions (source IP, MFA present)
  9. IAM Access Analyzer to find public / cross-account access and generate least-privilege policies
  10. Permission boundaries & SCPs (Organizations) as guardrails

Scenario questions — Module 1

An EC2 application must read files from an S3 bucket. A developer wants to paste his access key and secret into the app’s config file. What do you recommend and why?

Choose: an IAM role (e.g. S3ReadOnlyRole) attached to the EC2 instance through an instance profile, with a policy allowing only s3:GetObject on that bucket.

Why: the instance gets temporary, auto-rotated credentials from STS; nothing secret is stored on disk or in Git; follows least privilege.

Why not access keys: long-term keys can leak (GitHub, AMI snapshots), must be rotated manually, and give the developer's full permissions to the app.

KeywordsIAM roleinstance profileSTStemporary credentialsleast privilege
A company of 40 developers and 5 auditors joins AWS. Auditors must only view, never change, anything. How do you organise access?

Choose: two IAM groups – Developers (power-user-style policy scoped to dev resources) and Auditors (AWS managed ReadOnlyAccess / SecurityAudit). Add each person as an IAM user (or better, federate via IAM Identity Center), MFA enforced.

Why: permissions are managed once per group; a new joiner is one click; easy audit. Add an explicit Deny on destructive actions for Auditors for safety — explicit deny always wins.

Why not root user / shared login: no accountability, CloudTrail cannot tell who did what.

A user’s group policy allows s3:*, but a second policy attached directly to him denies s3:DeleteBucket. Can he delete a bucket? Explain the logic.

No. IAM evaluation: (1) everything starts as implicit deny; (2) if any applicable policy has an explicit Deny → denied, full stop; (3) else if any policy explicitly Allows → allowed. Explicit deny beats any allow. Draw the policy-evaluation flowchart.

2.1 Compute options & Amazon EC2

In simple words: EC2 is a virtual computer you rent by the second. You choose the OS image (AMI), size (instance type), disk (EBS), firewall (Security Group) and network (VPC/subnet). Stop it and you stop paying for compute.

Launching an instance – 7 choices

  1. AMI – OS + pre-installed software (template)
  2. Instance type – CPU, RAM, network (e.g. t3.micro)
  3. Network – VPC, subnet, public IP
  4. IAM role – permissions for the app
  5. User data – script that runs at first boot
  6. Storage – root + extra EBS volumes
  7. Tags, Security Group, Key pair (SSH login)

Other compute services (know one line each)

  • Lambda – serverless, run code on events, pay per ms, max 15 min
  • Elastic Beanstalk – PaaS, deploy code, AWS builds the infra
  • ECS / EKS / Fargate – run Docker containers
  • Lightsail – simple VPS with fixed monthly price
  • Outposts – AWS hardware in your own data centre

Built on the AWS Nitro System (security + performance); EC2 SLA 99.99%.

2.3 Elastic Load Balancing + Auto Scaling

In simple words: the Load Balancer is the receptionist who sends each visitor to a free, healthy server. Auto Scaling is the manager who hires more servers when it gets busy and lets them go when it's quiet — and replaces any that fall sick. Together they give high availability + elasticity + cost saving.

Auto Scaling Group (ASG)

  • Launch template – what to launch (AMI, type, SG, role).
  • Min / Desired / Max – ASG never goes below min.
  • Spreads instances across AZs; replaces unhealthy ones.
  • Policies: Target tracking (keep CPU at 50%), Step/simple (CloudWatch alarm → add N), Scheduled (9 am Monday add 10), Predictive (ML forecasts).
  • Mixed instances: On-Demand base + Spot top-up.

Elastic Load Balancer

  • Single DNS endpoint, spans multiple AZs.
  • Health checks – unhealthy targets get no traffic.
  • SSL/TLS termination (ACM certificate), sticky sessions.
  • Integrates with ASG, WAF (ALB), Shield.
  • Cross-zone load balancing.

2.4 Amazon S3 – object storage

In simple words: S3 is an infinite online locker. You put objects (any file + metadata) into buckets, and get them back with a URL/API from anywhere. It’s not a disk you mount — you upload/download whole objects.

  • Bucket name is globally unique; bucket lives in one Region; data copied across ≥3 AZs automatically (except One Zone).
  • Object up to 5 TB (single PUT 5 GB; use multipart upload above 100 MB). Unlimited objects. Identified by key (e.g. photos/2026/a.jpg).
  • Durability 11 nines (99.999999999%) – practically never lose data. Availability 99.99% for Standard.
  • URL styles: https://bucket.s3.region.amazonaws.com/key (virtual-hosted) or path-style.
  • Features: versioning (undo deletes), bucket policy / ACL / Block Public Access, encryption (SSE-S3, SSE-KMS, client-side), replication (CRR / SRR), static website hosting, event notifications (to Lambda/SQS/SNS), presigned URLs.
  • Pricing: pay GB-month + requests + data transfer OUT. Free: data IN, and OUT to CloudFront/EC2 in same Region.
  • Use cases: app assets, static websites, backup & DR, data lake / big-data staging, logs, media.

Glacier = deep-freeze warehouse for archives. Instance store = fast scratch disk physically in the host, wiped when the instance stops.

Scenario questions — Module 2

An e-commerce site gets 2,000 users normally but 50,000 during a 3-day festival sale. Design compute so it never crashes and doesn’t waste money the rest of the year.

Choose: Application Load Balancer + EC2 Auto Scaling Group across 2–3 AZs. Baseline (min) on Reserved/Savings Plans; extra on On-Demand (and Spot for stateless parts). Scheduled scaling before the sale + target tracking (CPU 50% / requests per target).

Why: elasticity — capacity follows demand; ALB health checks + multi-AZ = HA; you pay for 50k-user capacity only for 3 days.

Why not one huge instance (scale up): single point of failure, idle 362 days, downtime to resize. Why not all Reserved: paying for peak all year.

3.2 Amazon VPC, subnets, gateways & route tables

In simple words: a VPC is your own private, fenced-off network inside AWS. You choose its IP range, cut it into subnets (each subnet lives in exactly one AZ), and use route tables to say where traffic may go. A subnet is "public" only because its route table sends 0.0.0.0/0 to an Internet Gateway.

Building blocks

  • VPC – Regional; spans all AZs of the Region; CIDR /16–/28.
  • Subnet – range inside the VPC, one AZ only. Public or private.
  • Internet Gateway (IGW) – door between VPC and internet; one per VPC; horizontally scaled, HA.
  • NAT Gateway – lives in a public subnet; lets private instances go OUT (patches) but blocks inbound connections. One per AZ for HA.
  • Route table – rules "destination → target". Every table has the local route (VPC CIDR) that can't be removed. Each subnet associates with one table.
  • VPC endpoints – private access to S3/DynamoDB (gateway endpoint) or other services (interface endpoint, PrivateLink) without internet.

3.4 VPC Peering, Transit Gateway, VPN & Direct Connect

3.5 Amazon CloudFront (CDN)

In simple words: CloudFront keeps copies of your content in "local warehouses" (edge locations) near users worldwide, so a user in London gets your Mumbai-hosted site from London in milliseconds instead of across the planet.

  • Origin: S3 bucket, ALB, EC2, API Gateway, or any HTTP server. Distribution = configuration with a domain like d123.cloudfront.net.

  • Benefits: lower latency, offloads origin (fewer servers), lower data-transfer cost, DDoS absorption.

Amazon CloudWatch — performance monitoring

  • Metrics: CPU, network, disk, status checks (default every 5 min; detailed 1 min). Memory & disk-space need the CloudWatch Agent (OS-level metrics).
  • Alarms: threshold on a metric → SNS notification, Auto Scaling action, EC2 stop/reboot/recover.
  • Logs: collect app/system logs; Logs Insights to query; metric filters ("count ERROR").
  • Dashboards: graphs for ops teams.
  • Events / EventBridge: react to state changes on a schedule or event.

AWS CloudTrail — audit of API calls

  • Records every API call (console, CLI, SDK): who (identity), what (action), when, from where (source IP), on which resource.

  • Create a trail to keep logs forever in S3 (enable log-file integrity validation, encrypt with KMS), and stream to CloudWatch Logs for alarms ("root login").
  • Management events vs data events (S3 object-level, Lambda invoke).
  • Use: security investigations, compliance audits, "who deleted my bucket?".

AWS Config — configuration history & compliance

  • Records the configuration of each resource over time (timeline), and the relationships (this EC2 uses that SG).

6.2 AWS Key Management Service (KMS)

In simple words: KMS is a secure key safe. You never handle the master key — it never leaves KMS's hardware security modules. AWS services (S3, EBS, RDS, DynamoDB…) ask KMS to encrypt/decrypt for you, and every use is logged in CloudTrail.

7.1 Why integrate? Tight vs loose coupling

In simple words: if the web server calls the payment server directly and the payment server is slow or down, the website hangs — that's tight coupling. Put a queue or topic in between and each part can work, fail and scale on its own — that's loose coupling. Like a restaurant: waiters drop order slips on a rail (queue) instead of standing next to the chef.

Tightly coupled

Web → Order → Payment → Email (synchronous chain). One failure breaks all; scaling one means scaling all; slowest step sets the speed.

Loosely coupled

Web → SQS → Order workers; Order → SNS → (Payment, Email, Analytics). Failures are isolated, messages wait safely, each tier scales on its own queue depth.

7.7 Scalability & Elasticity · High Availability & Fault Tolerance

Scalability = the system can grow to handle more load (by design). Elasticity = it grows and shrinks automatically with demand, so you pay only for what you need.

  • Horizontal scaling (scale out) – add instances (ASG). Preferred.
  • Vertical scaling (scale up) – bigger instance; limited, downtime.
  • Stateless components → share state in DynamoDB/ElastiCache.
  • Event-driven – Lambda, Kinesis scale per event.
  • Decoupling – SQS/SNS so tiers scale independently.

High Availability = the system stays up most of the time (e.g. 99.99%), maybe with a brief blip during failover. Fault Tolerance = zero interruption even when a component fails (full redundancy running). FT ⊃ HA, and costs more.

  • Multi-AZ deployment (RDS Multi-AZ, ASG across AZs)
  • Cross-Region replication (S3 CRR, Aurora Global DB)
  • ELB health checks; Route 53 DNS failover; Elastic IP remap
  • Backups, snapshots, versioning

8.3 AWS Database Migration Service (DMS)

In simple words: DMS copies a database into AWS while the old one keeps running. It first copies everything (full load), then keeps copying new changes (CDC) until you're ready to switch, so downtime is only minutes. 8.4 AWS Server Migration Service (SMS)

In simple words: SMS copies your on-prem virtual machines (VMware vSphere, Hyper-V/SCVMM, Azure VMs) into AWS as AMIs, ready to launch as EC2 — a "lift-and-shift" tool.

10 golden rules that earn marks in any answer

  1. 2+ AZs for anything that must stay up (M1, M7)
  2. Only the load balancer is public; app & DB in private subnets (M3)
  3. Roles, not access keys; least privilege; MFA on root (M1)

  5. Scale out, not up: ELB + Auto Scaling, stateless app (M2, M7)
  6. Decouple with SQS/SNS so one failure doesn't spread (M7)
  7. Match pricing to workload: Spot / RI-SP / On-Demand (M2)
  8. Match storage to access: lifecycle → IA → Glacier (M2)
  9. Monitor & audit: CloudWatch + CloudTrail + Config (M5)

Module 1 Foundations & IAM

  • Cloud = rent, pay-as-you-go, OpEx, elastic. IaaS (EC2) · PaaS (Beanstalk) · SaaS (Gmail).
  • Region (geo, 2+ AZ) → AZ (isolated DCs) → Edge location (cache). Pick Region by compliance → latency → services → cost.
  • Shared responsibility: AWS = security OF cloud; you = IN cloud (data, IAM, guest OS, SG).
  • IAM is global & free. User (person) · Group (users only) · Role (temporary STS creds) · Policy (JSON: Effect, Action, Resource, Condition).
  • Evaluation: explicit Deny > explicit Allow > implicit Deny.

Draw: shared-responsibility layers; EC2 → role → S3.

Trap: groups can't nest; roles have no password.

Module 2 Compute & Storage

  • EC2 families: T/M general · C compute · R/X memory · P/G GPU · I/D storage.
  • Pricing: On-Demand (spiky) · RI/SP ≤72% (steady 1–3 yr) · Spot ≤90% (interruptible, 2-min notice) · Dedicated Host (BYOL).
  • Lifecycle: pending → running → stopping → stopped → terminated. Stop = keeps EBS, loses instance store & public IP.
  • ALB = L7 path/host · NLB = L4 TCP/UDP, static IP · GWLB = firewalls · ASG = min/desired/max, replaces unhealthy.
  • S3: object, 11 nines, 5 TB/object. Standard → Intelligent-Tiering → Std-IA → One Zone-IA → Glacier Instant/Flexible → Deep Archive (12–48 h).
  • EBS = block, 1 instance, same AZ (gp3, io2, st1, sc1) · EFS = shared NFS, multi-AZ · Instance store = ephemeral.

Draw: ALB + ASG across 2 AZs; S3 lifecycle timeline.

Trap: HDD EBS can't boot; One Zone-IA loses data if AZ dies.

Module 3 Networking & CDN

  • VPC = Regional private network, CIDR /16–/28. Subnet = one AZ. 5 IPs reserved (/24 → 251).
  • Public subnet = route 0.0.0.0/0 → IGW. Private → NAT GW (outbound only, sits in public subnet).
  • SG: instance, stateful, allow-only, can reference SGs. NACL: subnet, stateless, allow+deny, numbered.
  • Peering: 1-to-1, non-transitive, no overlapping CIDR. Many VPCs → Transit Gateway.
  • VPN: IPsec over internet, minutes, cheap. Direct Connect: dedicated fibre 1/10/100 Gbps, weeks, consistent.
  • CloudFront: edge cache, origin (S3/ALB), TTL, signed URLs, OAC, Shield Std built in.

Draw: VPC with 6 subnets in 2 AZs + route tables.

Trap: SG can't deny; A↔B↔C peering ≠ A↔C.

Module 4 Databases

  • RDS = managed MySQL/PostgreSQL/MariaDB/Oracle/SQL Server; AWS patches & backs up (1–35 days PITR).
  • Multi-AZ = sync standby, auto failover, HA, not readable. Read Replica = async, readable, up to 5, promotable, cross-Region.
  • Aurora: MySQL/PG compatible, 6 copies / 3 AZ, 15 replicas, failover <30 s, 5×/3× faster, ~20% pricier.
  • DynamoDB: NoSQL key-value, partition + sort key, ms at any scale, on-demand/provisioned, Global Tables, DAX.
  • Streams: ordered item changes, 24 h, NEW/OLD images → Lambda.

Draw: Multi-AZ vs Read Replica side by side.

Trap: Multi-AZ does NOT speed up reads.

  • CloudTrail = who did what (API log, 90-day history; trail → S3).
  • Config = what changed + is it compliant (rules, timeline, remediation).
  • Systems Manager = act on fleet (Patch Manager, Run Command, Session Manager, Parameter Store).

Module 6 Security & Compliance

  • EC2 OS patch = you; RDS engine patch = AWS; S3 bucket policy = you; physical = AWS.
  • KMS: managed keys in HSMs, customer-managed vs AWS-managed, rotation, key policy, CloudTrail audit, envelope encryption. CloudHSM = single-tenant.
  • WAF: Layer 7 web ACL on CloudFront/ALB/API GW — SQLi, XSS, rate-based, geo, IP sets.
  • Shield: Standard free L3/L4 DDoS; Advanced paid — 24×7 response team, L7, cost protection.
  • Best practices: least privilege, MFA, CloudTrail everywhere, encrypt everything, private subnets, GuardDuty/Inspector/Security Hub.

Draw: Users → CloudFront+Shield → WAF → ALB → private EC2 → KMS-encrypted RDS.

Trap: WAF can't attach to EC2 or NLB directly.

Module 7 Integration & Best Practices

  • SQS = queue, pull, 1 consumer, 4 days default / 14 max, 256 KB, visibility timeout, DLQ. Standard vs FIFO (order, exactly-once).
  • SNS = topic, push, many subscribers, fan-out, email/SMS. SNS+SQS = durable fan-out.
  • Step Functions = serverless visual state machine (Task, Choice, Parallel, Wait, Retry/Catch). SWF = legacy deciders + workers, human tasks.
  • EventBridge = event bus with rules · AppFlow = SaaS ↔ AWS data.
  • Well-Architected 6 pillars: Ops Excellence, Security, Reliability, Performance, Cost, Sustainability.
  • HA = quick recovery · FT = zero interruption. DR: Backup&Restore → Pilot Light → Warm Standby → Active-Active. RPO = data loss, RTO = downtime.

Draw: SNS fan-out to SQS queues; 6-pillar temple.

Trap: Lambda max 15 min → long workflows need Step Functions.

Module 8 Migration & Hybrid

  • Phases: Assess → Plan → Migrate → Execute/test → Optimise.
  • 7 Rs: Retire, Retain, Rehost (lift & shift), Relocate, Replatform (to RDS), Repurchase (SaaS), Refactor (cloud-native).
  • DMS: live DB migration, full load + CDC, source stays up. Different engines → SCT first.
  • SMS: agentless, incremental VM replication (VMware/Hyper-V) → AMI. (Today: MGN.)
  • Snowball ~80 TB offline · Snowball Edge + compute at edge · Snowmobile 100 PB truck. >1 week online → Snow.
  • Hybrid: DX + VPN backup, Storage Gateway, DataSync, Outposts, AD federation.

Draw: Oracle → SCT → DMS → Aurora PostgreSQL.

Trap: DMS moves databases, not VMs; Snowball can't keep a live DB in sync.

Transfer-time formula (M8) — practise once

time (s) = data in bits ÷ bandwidth in bits/s. 1 TB = 8 × 1012 bits. 100 TB at 1 Gbps = 8×1014 ÷ 109 = 8×105 s ≈ 9.3 days. Same at 100 Mbps ≈ 93 days → Snowball.

CIDR (M3): IPs = 2(32 − prefix); usable in AWS = that − 5. /24 → 251, /26 → 59, /28 → 11.

Availability (M7): 99.9% ≈ 8.8 h/yr down · 99.99% ≈ 53 min/yr · 99.999% ≈ 5 min/yr.
